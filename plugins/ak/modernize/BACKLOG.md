# Plugin Completion Backlog

State as of 2026-08-03. Scope set by the user: **finish the plugin and make the workflow
actually automate building an app.** Fixing bugs in the A01 instance is out of scope and

Current contents: 9 method documents, 10 templates, 1 skill. Placeholder coverage is
near-complete — of 69 keys a project must fill, **60 have at least one consumer**.

## The central gap

The plugin **describes** its orchestration; it does not **encode** it.

`MASTER_WORKFLOW.md` and `SKILL.md` mention "background agent", "subagent" or "parallel"
**10 times** — most concretely in Multi-Screen Batch, which instructs "one background
agent per group, screens within a group run sequentially, subagents report HIGH gate
findings to the parent rather than prompting". But the plugin ships **no `agents/`, no
`commands/`, and no `hooks/`**. Every run therefore re-derives the orchestration from
prose, and the gates ("`{{LINT_CMD}}` passes") hold only as long as the agent chooses to
honour them.

**That gap is now closed.** D1, D4, D5 and D6 are done: the plugin ships a validator, an
orchestration policy set with an envelope-based write allowlist, five per-stage commands, and
a non-writing scope sensor. What remains in T2 is D2 (bootstrap), which gains most of its value once the phase output exists.

## Priority

**T1 → T2 → T3 → T4.** All five open decisions are now settled, so nothing is blocked. D1 is **done**, so the remaining work can be self-verified by running it rather than
reviewed by hand.

## Stage 0 seam — what is safe to build on, and what waits for 2.8

2.8 is in progress. The question is not "wait or not" but **which parts of the seam are
stable**, and that is answerable with evidence rather than guesswork: the files this pipeline
consumes were **byte-identical across the 2.6.1 to 2.7.1 bump**, a release that added
thirteen schemas and changed none of them.

### Build on these now — stable, required, documented

Each is listed in `specifications/output-contract.yaml` (v2.1) as a required output or run
artifact, and each is byte-identical between 2.6.1 and 2.7.1.

| Artifact | Gives | Used by |
|---|---|---|
| the six phase documents | screen inventory, per-screen analysis, workflows, business rules | C3, C3c |
| `Evidence.json` / `evidenceItem` | `source_path`, `source_location`, `source_sha256`, `status`, `source_language` | C3b anchors |
| `TraceabilityMatrix.csv` / `traceability-row` | `screen`, `vba_event`, `processing`, `data_target`, `output`, `evidence_ids` | G2 rule coverage |
| `run-state.json` / `phase_gates` | per-phase `PENDING \| READY \| PUBLISHED \| REJECTED`, a **required** field | C3c pre-flight |
| `QuestionList.md`, `QA_Report.md` | open questions, independent QA | C3, Stage 5 |
| `handoff.schema.json` | worker handoff shape | reference for the group envelope |

### Treat these as optional enrichment — new in 2.7.1, may move in 2.8

| Artifact | Why not required |
|---|---|
| `phase-readiness.json` | Richer than `phase_gates` - it adds `LIMITED` as a distinct state plus `reasons` and `rule_ids` - but it is new, and it lands in `<output_root>/<bundle_id>/` with **no pointer to the current bundle**: `run-state.json` has no `bundle_id` field, so a consumer must discover the directory. Read it when found; degrade to `phase_gates` when not |
| `coverage.json`, `failures/extraction-failures.json` | Same bundle directory, same discovery problem. Valuable for G1 - non-zero `skipped`, `failed` or `unsupported` is a finding with no judgement needed - so consume when present and say so |
| manifest v2.2, acquisition adapters, classification rules | Upstream of the seam. This pipeline never reads them |

**The rule that follows:** read the stable tier as required, read the 2.7.1 additions if
present, and **state in the pre-flight report which tier was used**. Silent degradation is the
failure to avoid - a run that quietly fell back to the weaker signal looks identical to one
that had the stronger.
